# Проект: витрины данных для рекомендательной системы книг

## 1. Описание задачи

В этом проекте реализован ETL-пайплайн на PySpark для обработки данных сервиса Яндекс Книги. Основная цель - собрать пять аналитических витрин с разной детализацией для дальнейшего построения рекомендаций (ранжирование контента, учет платформы, дня недели, гео и решение проблемы холодного старта).

Состав витрин:
1. `user_content_mart` - связка пользователя с конкретной книгой: сколько слушал в часах, сколько было сессий, процент дочитывания и флаг завершения.
2. `user_genre_mart` - интересы читателя по жанрам: суммарные часы, ранг жанра по часам, количество дочитанных книг, а также детского и взрослого контента.
3. `user_mart` - сводный профиль читателя: активность, любимый жанр, платформа, формат и средний процент дочитывания.
4. `content_mart` - метрики по книгам: популярность среди читателей, охват, средняя дочитываемость и число платформ.
5. `daily_user_mart` - активность пользователя по дням: дата, день недели, сколько книг слушал и сколько часов потратил.

## 2. Как запускать проект

Скрипт запускается через консоль через python или через spark-submit.

Так как кластер YARN сейчас на техобслуживании и недоступен, расчеты настроены по умолчанию на `local[*]`. В скрипте сохранена поддержка запуска на кластере: если передать `--master yarn`, сессия инициализируется под YARN.

### Требования к окружению:
- Python 3.10-3.12 (установка зависимостей: `pip install -r requirements.txt`);
- Java: JDK 8, 11 или 17 с настроенной переменной `JAVA_HOME`.

### Особенности запуска и ресурсов:
- Память драйвера: задана `8g` по ТЗ (локально для тестов хватает и `4g`).
- Локальный режим и YARN: при `--master "local[*]"` всё работает в одном процессе JVM драйвера, поэтому настройки памяти экзекуторов (`spark.executor.*`) Spark просто игнорирует. На кластере YARN под них уже выделяются отдельные контейнеры.
- Авторизация S3: локально ключи берутся из файла `.env`, а на кластере доступ обычно настраивается централизованно через роли или конфиги.

### Аргументы командной строки main.py:
- `--start-date` - начало периода выборки (ГГГГ-ММ-ДД);
- `--end-date` - конец периода выборки (ГГГГ-ММ-ДД);
- `--geo-id` - фильтр по региону (например, "Москва, Россия");
- `--columns` - колонки для вывода распределения аудитории (например, usage_platform_ru genre);
- `--audition-path` - путь к файлу с сессиями `audition.parquet` (S3 или локальный);
- `--content-path` - путь к файлу с каталогом `content.parquet` (S3 или локальный);
- `--output-path` - папка, куда сохранять витрины в Parquet;
- `--master` - мастер Spark (`local[*]` по умолчанию или `yarn`);
- `--show-plan` - распечатать в консоль расширенный план выполнения для `user_mart`;
- `--show-analytics` - показать распределения по контенту, дням недели и городам;
- `--verbose` - подробный вывод промежуточных шагов, схем и проверок данных.

### Способы запуска:

Через spark-submit:
- Windows: `submit.bat`
- Linux: `./submit.sh`

Либо напрямую через python:
```bash
python main.py \
  --master 'local[*]' \
  --start-date 2024-11-01 \
  --end-date 2024-11-30 \
  --geo-id "Москва, Россия" \
  --columns usage_platform_ru genre \
  --show-analytics \
  --show-plan
```

Параметры подключения к S3 вынесены в файл `.env` (шаблон лежит в `.env.example`):
```dotenv
S3_ENDPOINT_URL=https://storage.yandexcloud.net
S3_ACCESS_KEY_ID=your_access_key
S3_SECRET_KEY=your_secret_key
S3_SOURCE_BUCKET=s3-ds-source
S3_OUTPUT_BUCKET=your_output_bucket
```

## 4. Очистка данных и распределения

### Что сделано при очистке:
1. Дата `msk_business_dt_str` переведена из строки в формат даты Date. Для суточной аналитики этого достаточно; если бы решалась задача почасовых рекомендаций, сохранялся бы полный timestamp.
2. Проверена длительность сессий `hours` и `hours_sessions_long`: убраны строки с пропусками и значениями меньше 0 или больше 24 часов. Удалилось ровно 56 аномальных строк. В таблице осталось 1 002 840 сессий.
3. В `app_version` заполнены пропуски значением `unknown`.
4. В каталоге книг для 7 некорректных значений длительности посчитана медиана по валидным книгам: получилось 7.4668183 часа, подставлена вместо пропусков и нулей.
5. Сделан inner join сессий с каталогом по `main_content_id`. Получилось 996 509 строк (выпало 6 331 сессий, которых не оказалось в каталоге, это меньше 1%). Проверка показала полное отсутствие дубликатов по `audition_id`.
6. Жанры из строки `published_topic_title_list` разбиты в массив через split, почищены от кавычек и пробелов по краям.

## 6. Разбор физического плана выполнения user_mart

План построен через метод `explain(mode="extended")` и сохранен вывод в файл `exec_plan_local.md`. Проанализирован блок `Physical Plan`.

### 1. Перемешивание данных (Shuffle)
В плане за перемешивание отвечают операторы `Exchange hashpartitioning`:
- Всего в плане 27 таких узлов Exchange.
- Они возникают перед группировками по пользователю (`puid`), перед джойнами и перед оконными функциями `row_number()`, когда вычисляются любимый жанр, любимая платформа и тип контента.
- В ветке жанров шаффл идет по паре ключей `(puid, main_content_id)`, что дает дополнительную нагрузку на сеть.

### 2. Типы соединений (Join)
- Соединение таблицы сессий с каталогом идет через `SortMergeJoin Inner`. Чтобы драйвер не падал по памяти при авто-бродкасте, был отключен broadcast (`autoBroadcastJoinThreshold = -1`). Поэтому обе таблицы шардируются по `main_content_id`, сортируются узлами `Sort` и соединяются слиянием.
- Итоговая витрина `user_mart` собирается через цепочку из пяти последовательных `SortMergeJoin LeftOuter` по ключу `puid`, которые цепляют любимый жанр, формат, платформу, дочитываемость и жанровые агрегаты.

### 3. Самые тяжелые операции
- Многократное чтение файлов: узел `FileScan parquet` по таблице сессий `audition` вызывается 7 раз. Из-за того, что датафрейм не кэшировался, Spark для каждого блока метрик заново перечитывал parquet с диска.
- Ветка `favorite_genre`: операция `Generate explode` размножает строки для каждого жанра книги, а затем идет джойн по двум полям и оконная сортировка. Это самая ресурсоемкая часть.

### 4. Что можно оптимизировать в плане:
1. **Broadcast Join каталога контента (`F.broadcast(con_df)`)**: это ключевая оптимизация. Каталог книг весит всего около 2 МБ (31.6 тыс. строк), что в разы меньше стандартного лимита памяти на broadcast (10 МБ). Явный бродкаст каталога устраняет самый тяжелый shuffle миллиона строк сессий, причем хинт `broadcast()` в коде сработает даже при выключенном глобальном авто-бродкасте (`autoBroadcastJoinThreshold = -1`).
2. **Кэширование объединенных данных (`cache` / `persist`)**: если после фильтрации и джойна сессий с каталогом сохранить датафрейм в памяти, Spark не будет сканировать parquet с диска 7 раз, а прочитает данные из памяти один раз.
3. **Физическое переиспользование уже рассчитанных витрин**: в коде витрины `user_content_mart` и `user_genre_mart` уже передаются как аргументы в `build_user_mart`. Но так как Spark ленивый и кэширования нет, Catalyst всё равно разворачивает план до диска и пересчитывает их. Чтобы переиспользование сработало на самом деле, витрины нужно закэшировать через `.cache()` или сохранить на диск в parquet и прочитать перед сборкой `user_mart`.
4. **Подсчет уникальных жанров**: метрику `unique_genres_count` можно посчитать простым `count` по уже развернутой витрине `user_genre_mart`, не делая повторный `explode` массива жанров.
